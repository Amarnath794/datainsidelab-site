Python & SQL

Python vs SQL for data analysts and data engineers

SQL and Python are not competitors. They are two practical ways to work with data—and the right choice depends on the question, the size of the data, and whether you are finding an answer or building a dependable system.

November 10, 2026 · 14 min read

Start with the simple answer

Use SQL when your question is mainly about data already stored in relational tables: filter rows, join tables, aggregate revenue, calculate cohorts, or create a report. Use Python when you need flexible programming: custom logic, statistical analysis, a reusable application, an API call, a machine-learning workflow, or a chart that goes beyond your BI tool.

For data engineering, Python becomes even more useful. It can orchestrate jobs, call services, validate files, and transform data. When the data is large and distributed, engineers often use PySpark: Python code that tells a Spark cluster how to process data in parallel.

The important point: most strong data professionals use both. SQL expresses set-based questions clearly; Python adds programming flexibility; PySpark brings that flexibility to large-scale data processing.

The same business question, different tools

Suppose a retail team asks: “Which product categories are growing, and are repeat customers driving the growth?” An analyst might answer the first part entirely in SQL. They may then bring the result into Python to examine distributions, test an idea, or create a tailored chart. The engineer makes sure the underlying orders and customers arrive correctly every day.

SQL analysis: concise answers from tables

SQL is declarative. You say what result you want, and the database decides the execution plan. That is why a well-written query can be compact even when it scans a large table.

This BigQuery-style query groups completed orders by month and product category. It uses a CTE to calculate monthly revenue and a window function to measure growth against the previous month.

WITH monthly_category_sales AS (
  SELECT
    DATE_TRUNC(order_date, MONTH) AS order_month,
    product_category,
    SUM(order_amount) AS revenue,
    COUNT(DISTINCT order_id) AS orders,
    COUNT(DISTINCT customer_id) AS customers
  FROM analytics.fact_orders
  WHERE order_status = 'completed'
    AND order_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 12 MONTH)
  GROUP BY 1, 2
)
SELECT
  order_month,
  product_category,
  revenue,
  orders,
  customers,
  ROUND(100 * SAFE_DIVIDE(
    revenue - LAG(revenue) OVER (
      PARTITION BY product_category ORDER BY order_month
    ),
    LAG(revenue) OVER (
      PARTITION BY product_category ORDER BY order_month
    )
  ), 1) AS month_over_month_growth_pct
FROM monthly_category_sales
ORDER BY order_month DESC, revenue DESC;

This is excellent analyst SQL: the metric is visible, the grain is clear, and the result can feed a dashboard immediately. SQL is usually the first choice when the data warehouse already contains the information needed for the question.

Python analysis: explore, model, and communicate

Python does not replace that SQL query. It extends what happens next. An analyst can use Python to pull a controlled result set from the warehouse, combine it with a CSV or API response, calculate a custom measure, run a statistical method, and create a chart in one reproducible notebook.

Below, the SQL query still does the heavy filtering and aggregation in the warehouse. Python, using pandas, then calculates each category’s share of revenue and flags unusually large changes. This is a good pattern: let the warehouse process warehouse-sized data, then use Python on a focused analysis dataset.

import pandas as pd
from sqlalchemy import create_engine

engine = create_engine("warehouse-connection-string")

query = """
SELECT
  DATE_TRUNC(order_date, MONTH) AS order_month,
  product_category,
  SUM(order_amount) AS revenue
FROM analytics.fact_orders
WHERE order_status = 'completed'
  AND order_date >= CURRENT_DATE - INTERVAL '12 months'
GROUP BY 1, 2
"""

sales = pd.read_sql(query, engine)
sales["order_month"] = pd.to_datetime(sales["order_month"])

sales["category_share_pct"] = (
    sales["revenue"]
    / sales.groupby("order_month")["revenue"].transform("sum")
    * 100
)

sales["growth_pct"] = (
    sales.sort_values("order_month")
         .groupby("product_category")["revenue"]
         .pct_change()
         .mul(100)
)

unusual_changes = sales.loc[
    sales["growth_pct"].abs() >= 25,
    ["order_month", "product_category", "revenue", "growth_pct"]
].sort_values("growth_pct")

print(unusual_changes)

Python is especially useful when the question changes while you investigate. You can add a chart, fit a forecast, call a geocoding API, or package the work into a reusable function. But Python also gives you more responsibility: you need to manage environments, dependencies, memory, and reproducibility.

SQL vs Python for analysts

Use SQL when

The data is already in tables

You need joins, filters, aggregation, cohorts, funnels, rankings, or a clean dataset for BI. SQL is often easier for another analyst to review.

Use Python when

The analysis needs more freedom

You need statistics, machine learning, text processing, external APIs, custom visualizations, or reusable analytical code.

There is no prize for using Python when SQL is enough. For a simple dashboard metric, a clear SQL query is usually faster to write, cheaper to run, and easier to maintain. Conversely, forcing complex loops, file parsing, or statistical logic into SQL can make the work harder than it needs to be.

What changes for data engineers?

Data engineers care about the question too, but their main responsibility is different: create a dependable path from source data to analytics-ready data. They work with raw events, late updates, duplicates, schema changes, permissions, job failures, and cost.

SQL remains central. It is excellent for modelling warehouse tables and defining business transformations. But engineering often needs procedural control around that SQL: checking whether a file arrived, reading an API page by page, triggering a job, or sending an alert. That is where Python is valuable.

Engineer SQL: model clean, reusable tables

Here is a simplified incremental SQL transformation. It keeps only the latest record for each order and merges it into an analytics fact table. The essential engineering idea is idempotency: running a job again should correct the table, not duplicate revenue.

MERGE analytics.fact_orders AS target
USING (
  SELECT
    order_id,
    customer_id,
    CAST(order_total AS NUMERIC) AS order_amount,
    DATE(order_created_at) AS order_date,
    LOWER(TRIM(order_status)) AS order_status,
    updated_at
  FROM raw.app_orders
  QUALIFY ROW_NUMBER() OVER (
    PARTITION BY order_id
    ORDER BY updated_at DESC
  ) = 1
) AS source
ON target.order_id = source.order_id
WHEN MATCHED AND source.updated_at > target.updated_at THEN
  UPDATE SET
    customer_id = source.customer_id,
    order_amount = source.order_amount,
    order_date = source.order_date,
    order_status = source.order_status,
    updated_at = source.updated_at
WHEN NOT MATCHED THEN
  INSERT (order_id, customer_id, order_amount, order_date, order_status, updated_at)
  VALUES (source.order_id, source.customer_id, source.order_amount,
          source.order_date, source.order_status, source.updated_at);

This is not analyst reporting SQL. It protects a shared data product. In a real project, the engineer would add data tests, partitioning, documentation, monitoring, and a scheduler such as Airflow, Fabric Data Factory, or a managed cloud service.

Engineer Python and PySpark: orchestrate and scale

Ordinary Python is useful for the “glue” around a pipeline: configuration, API ingestion, file checks, logging, and notifications. PySpark is used when transformations need a distributed compute engine. It looks like Python, but operations such as filter, groupBy, and join are translated into work executed across a Spark cluster.

The following PySpark example reads raw order files, standardizes columns, removes duplicate order versions, and writes a curated Delta table. It represents the same data-quality intent as the SQL MERGE, but is designed for a large lakehouse workload.

from pyspark.sql import functions as F
from pyspark.sql.window import Window

raw_orders = spark.read.format("json").load(
    "abfss://landing@storageaccount.dfs.core.windows.net/orders/"
)

latest_order_window = Window.partitionBy("order_id").orderBy(
    F.col("updated_at").desc()
)

clean_orders = (
    raw_orders
    .filter(F.col("order_id").isNotNull())
    .withColumn("order_amount", F.col("order_total").cast("decimal(18,2)"))
    .withColumn("order_date", F.to_date("order_created_at"))
    .withColumn("order_status", F.lower(F.trim("order_status")))
    .withColumn("row_number", F.row_number().over(latest_order_window))
    .filter((F.col("row_number") == 1) & (F.col("order_amount") >= 0))
    .select("order_id", "customer_id", "order_amount",
            "order_date", "order_status", "updated_at")
)

(clean_orders.write
    .format("delta")
    .mode("overwrite")
    .option("overwriteSchema", "true")
    .saveAsTable("analytics.fact_orders"))

Do not use PySpark merely because it sounds advanced. For a small, well-structured warehouse transformation, SQL can be clearer and cheaper. PySpark becomes compelling when data is too large for one machine, when you work in a lakehouse, or when you need programmatic transformations over many files and sources.

A practical decision guide

  1. Start with the data location. If it is in a warehouse, begin with SQL. If it is in files, APIs, or multiple services, Python may be part of the entry point.
  2. Start with the smallest suitable tool. A simple metric deserves simple SQL; a large distributed transformation may deserve PySpark.
  3. Push heavy work to the compute engine. Avoid downloading millions of rows to a local pandas notebook when SQL or Spark can aggregate them first.
  4. Design for the next person. Use clear names, documented metric definitions, tests, and repeatable code—regardless of language.
  5. Learn in sequence. Build strong SQL first, then learn Python fundamentals and pandas, and finally learn PySpark after you understand dataframes and data-engineering basics.

Final takeaway

SQL answers table-shaped questions beautifully. Python makes analysis programmable and flexible. PySpark lets engineers apply dataframe-style logic to distributed data. The best data teams do not ask which language wins; they choose the smallest reliable tool that turns raw data into a trustworthy decision.
