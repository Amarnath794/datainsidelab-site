SQL for data analysts vs data engineers: the same language, different job

Both roles write SQL, but they are solving different problems. Analysts use SQL to answer business questions. Data engineers use SQL to create the dependable data models that make those answers possible.

November 10, 2026 · 8 min read

One language, two points of view

Imagine an ecommerce company asks, “How did monthly revenue change, and which customer groups drove the change?” An analyst starts with a trusted, ready-to-use table and investigates the result. An engineer works further upstream: they clean incoming order data, remove duplicates, and build the table the analyst can trust.

Data analyst

Turn data into a decision

Writes readable queries against curated tables, explores patterns, validates a number, and communicates what it means to the business.

Data engineer

Turn raw events into trusted data

Builds transformations that are reliable, repeatable, efficient, observable, and safe to run again tomorrow.

How an analyst writes SQL

An analyst normally begins with business-friendly models such as analytics.fact_orders and analytics.dim_customers. The data is already cleaned and documented. The analyst’s SQL is focused on the question, not on repairing the source system.

Here is a mid-level example. It calculates monthly revenue by customer segment, then compares each month with the previous month using the LAG window function.

WITH monthly_revenue AS (
  SELECT
    DATE_TRUNC(order_date, MONTH) AS order_month,
    customer_segment,
    SUM(order_amount) AS revenue,
    COUNT(DISTINCT order_id) AS orders
  FROM analytics.fact_orders
  WHERE order_status = 'completed'
    AND order_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 12 MONTH)
  GROUP BY 1, 2
), with_previous_month AS (
  SELECT
    *,
    LAG(revenue) OVER (
      PARTITION BY customer_segment
      ORDER BY order_month
    ) AS previous_month_revenue
  FROM monthly_revenue
)
SELECT
  order_month,
  customer_segment,
  revenue,
  orders,
  ROUND(
    100 * SAFE_DIVIDE(revenue - previous_month_revenue,
                      previous_month_revenue),
    1
  ) AS month_over_month_growth_pct
FROM with_previous_month
ORDER BY order_month DESC, revenue DESC;

The output can become a dashboard, a slide, or a recommendation: for example, “Enterprise customers grew 18% month over month, while new-customer revenue declined.” Notice the priorities: clear names, the correct metric definition, and a result another person can review.

How an engineer writes SQL

The engineer’s work happens before that analyst query. Suppose order events arrive from an application and can be duplicated, incomplete, or updated after first arriving. The engineer must make a stable fact_orders table that can be run repeatedly without inflating revenue.

This BigQuery Standard SQL example first keeps the newest version of every order, standardizes data types, and then incrementally merges the clean records into an analytics table. Exact functions vary slightly across BigQuery, Snowflake, Databricks, and Fabric.

MERGE analytics.fact_orders AS target
USING (
  WITH ranked_raw_orders AS (
    SELECT
      order_id,
      customer_id,
      CAST(order_total AS NUMERIC) AS order_amount,
      DATE(order_created_at) AS order_date,
      LOWER(TRIM(order_status)) AS order_status,
      updated_at,
      ROW_NUMBER() OVER (
        PARTITION BY order_id
        ORDER BY updated_at DESC
      ) AS row_number
    FROM raw.app_orders
    WHERE order_id IS NOT NULL
      AND updated_at >= @last_successful_run
  )
  SELECT
    order_id, customer_id, order_amount, order_date, order_status, updated_at
  FROM ranked_raw_orders
  WHERE row_number = 1
    AND order_amount >= 0
) AS source
ON target.order_id = source.order_id
WHEN MATCHED AND source.updated_at > target.updated_at THEN
  UPDATE SET
    customer_id = source.customer_id,
    order_amount = source.order_amount,
    order_date = source.order_date,
    order_status = source.order_status,
    updated_at = source.updated_at
WHEN NOT MATCHED THEN
  INSERT (order_id, customer_id, order_amount, order_date, order_status, updated_at)
  VALUES (source.order_id, source.customer_id, source.order_amount,
          source.order_date, source.order_status, source.updated_at);

This code is not trying to tell a business story yet. Its job is to protect the story: one current row per order, valid amounts, predictable types, and a safe incremental update. In a production pipeline, the engineer would also add tests, freshness checks, permissions, scheduling, and alerts.

A useful rule: analysts optimize SQL for insight and communication; engineers optimize SQL for reliability and reuse. Strong data teams need both.

Where the roles overlap

The boundary is not a wall. Analysts often use advanced window functions, query optimization, and data quality checks. Engineers investigate business definitions and work closely with analysts to design useful models. In a small company, one person may do both jobs.

The most practical way to learn is to build from the analyst side outward:

  1. Learn SELECT, WHERE, GROUP BY, joins, and aggregates.
  2. Practice CTEs and window functions such as ROW_NUMBER, RANK, and LAG.
  3. Learn to read a data model and write metrics carefully.
  4. Then add engineering concepts: raw vs curated data, incremental loads, deduplication, testing, orchestration, and performance.

Final takeaway

SQL is a shared language across data careers. The difference is less about whether someone can write a join and more about what they are accountable for after the query runs. The analyst asks, “What should we do?” The engineer makes sure the data is ready for that question every day.
